# B6 실습 가이드

`01_schema.sql` ~ `04_bonus.sql`이 무엇을 하는지 DataGrip에서 직접 실행하면서 이해하기 위한 가이드입니다.
1단계부터 순서대로 진행하면 과제 목표(PK/FK, JOIN, GROUP BY, 트랜잭션, 인덱스)를 한 번씩 손으로 확인하게 됩니다.

**실습 규칙 하나:** 쿼리를 실행하기 전에 결과를 먼저 예측해 보세요. "몇 행이 나올까?", "에러가 날까?"를 정하고 실행해서 맞춰 보는 것이 가장 빨리 느는 방법입니다. 이 가이드의 예상 결과는 모두 MySQL 8.0에서 실제로 실행한 값입니다.

## 전체 구조 한눈에 보기

```
store 1 ──── N inventory N ──── 1 product
  │                                  │
  1                                  1
  │                                  │
  N                                  N
orders 1 ──── N order_item ──────────┘
  │
  1
  │
  N
payment
```

| 테이블 | 한 행의 의미 | 가리키는 테이블 (FK) |
|---|---|---|
| `store` | 가게 하나 | 없음 |
| `product` | 상품 하나 | 없음 |
| `inventory` | "어느 가게에 어떤 상품이 몇 개" | `store`, `product` |
| `orders` | 구매 한 건 | `store` |
| `order_item` | 구매 한 건에 담긴 상품 하나 | `orders`, `product` |
| `payment` | 결제 한 건 (나눠 내면 한 구매에 여러 건) | `orders` |

읽는 법: **FK를 가진 쪽이 N**입니다. `inventory`가 `store_id`를 갖고 있으니 "가게 1개 : 재고 행 N개"입니다.

### 파일 읽는 순서

1. `01_schema.sql` — 테이블과 규칙(제약조건). 아래 1~2단계에서 다룹니다.
2. `02_data.sql` — 샘플 데이터. 맨 위 주석에 "일부러 넣은 경우" 목록이 있습니다. 쿼리 결과가 왜 그렇게 나오는지 궁금할 때 여기를 보세요.
3. `03_queries.sql` — 과제 쿼리 15개. 3~8단계가 이 쿼리들을 변형하며 진행됩니다.
4. `04_bonus.sql` — 보너스.

## 1단계. 테이블 구조 살펴보기

```sql
SHOW TABLES;
DESCRIBE inventory;
SHOW CREATE TABLE inventory;
```

`SHOW CREATE TABLE` 결과에서 다음을 찾아보세요.

- `PRIMARY KEY (inventory_id)` — 행 하나를 구별하는 번호
- `UNIQUE KEY uk_inventory_store_product (store_id, product_id)` — 같은 가게에 같은 상품 행이 두 개 생기지 않게 막음
- `FOREIGN KEY (store_id) REFERENCES store (store_id)` — `store`에 있는 번호만 넣을 수 있음
- `CHECK (quantity >= 0)` — 재고는 음수가 될 수 없음

**생각해 보기:** 재고 수량을 `product` 테이블에 컬럼으로 두면 무엇이 문제일까요?
→ 가게가 10개인데 수량 칸은 하나라서, 가게별 수량을 저장할 곳이 없습니다. 그래서 "가게 × 상품" 조합마다 한 행을 두는 `inventory`가 필요합니다. 엑셀이었다면 시트를 가게마다 복사했을 텐데, DB는 관계로 풉니다.

## 2단계. 제약조건을 일부러 깨보기

DB가 엑셀과 다른 가장 큰 점은 **잘못된 데이터를 거부한다**는 것입니다. 아래 7개는 전부 에러가 나야 정상이고, 에러가 나므로 데이터는 바뀌지 않습니다.

```sql
-- (a) NOT NULL : 가격을 비워서 상품 등록
INSERT INTO product (name, barcode, price) VALUES ('테스트', '9999999999999', NULL);

-- (b) UNIQUE : 이미 있는 바코드로 상품 등록
INSERT INTO product (name, barcode, price) VALUES ('중복 바코드', '8801000000011', 100);

-- (c) CHECK : 재고를 음수로
UPDATE inventory SET quantity = -1 WHERE inventory_id = 1;

-- (d) CHECK : 정해지지 않은 상태값
INSERT INTO orders (store_id, total_amount, status) VALUES (1, 1000, 'DONE');

-- (e) 복합 UNIQUE : 강남점(1)에 생수(1) 재고 행을 하나 더
INSERT INTO inventory (store_id, product_id, quantity) VALUES (1, 1, 5);

-- (f) FK : 없는 상품(999)을 구매 내역에
INSERT INTO order_item (order_id, product_id, quantity, unit_price) VALUES (1, 999, 1, 1000);

-- (g) FK : 구매 내역이 달린 구매를 바로 삭제
DELETE FROM orders WHERE order_id = 1;
```

| | 에러 | 의미 |
|---|---|---|
| (a) | `1048 Column 'price' cannot be null` | 꼭 있어야 하는 값이 빠짐 |
| (b) | `1062 Duplicate entry '8801000000011'` | 중복 불가 컬럼에 같은 값 |
| (c) | `3819 Check constraint 'ck_inventory_quantity' is violated` | 규칙(0 이상) 위반 |
| (d) | `3819 Check constraint 'ck_orders_status' is violated` | 허용 목록에 없는 값 |
| (e) | `1062 Duplicate entry '1-1'` | (가게, 상품) 조합 중복 |
| (f) | `1452 Cannot add or update a child row` | 자식이 없는 부모를 가리킴 |
| (g) | `1451 Cannot delete or update a parent row` | 자식이 남아 있는 부모를 지우려 함 |

(f)와 (g)가 FK의 두 방향입니다. **자식은 없는 부모를 가리킬 수 없고, 부모는 자식이 남아 있으면 지워지지 않습니다.**

> 참고: (a)에서 `price`를 아예 빼고 `INSERT INTO product (name, barcode) ...`로 실행하면 `1364 Field 'price' doesn't have a default value`가 납니다. 같은 NOT NULL 위반인데, "값을 안 줬고 기본값도 없다"는 뜻입니다.

## 3단계. SELECT가 실행되는 순서

쿼리는 적힌 순서와 실행되는 순서가 다릅니다.

```
적는 순서 :  SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
실행 순서 :  FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

확인해 봅시다. `SELECT`에서 만든 별칭을 `WHERE`에서 쓰면 어떻게 될까요?

```sql
SELECT name, price * 2 AS double_price
FROM product
WHERE double_price > 5000;
```

→ `1054 Unknown column 'double_price' in 'where clause'`. `WHERE`가 `SELECT`보다 먼저 실행되므로 그 시점에는 별칭이 아직 없습니다. 반대로 `ORDER BY double_price`는 `SELECT` 뒤라서 동작합니다.

**해볼 것:** `03_queries.sql`의 Q01~Q04를 실행하고, 각각 `WHERE`·`ORDER BY`·`LIMIT`을 하나씩 지워서 결과가 어떻게 바뀌는지 보세요.

## 4단계. JOIN

### 4-1. INNER JOIN : 번호를 이름으로 바꾸기

`inventory`에는 숫자(`store_id`, `product_id`)만 있습니다. 이름을 보려면 부모 테이블을 붙여야 합니다. Q05를 실행한 뒤, 먼저 JOIN 없이 보세요.

```sql
SELECT * FROM inventory WHERE store_id = 1;
```

그리고 Q05와 비교합니다. `ON s.store_id = i.store_id`는 "inventory 행의 store_id와 같은 번호를 가진 store 행을 옆에 붙여라"라는 뜻입니다.

Q06은 4개 테이블을 붙입니다. `orders → order_item → product` 순서로 FK를 따라가는 길을 손가락으로 짚으면서 읽어 보세요.

### 4-2. INNER vs LEFT : 짝이 없는 행은 어떻게 되나

Q07을 실행하면 10개 가게가 모두 나오고, 대전둔산점·제주공항점은 0건입니다. 이제 `LEFT JOIN`을 `INNER JOIN`으로 바꿔 실행해 보세요.

```sql
SELECT s.name, COUNT(o.order_id) AS paid_order_count
FROM store s
INNER JOIN orders o ON o.store_id = s.store_id AND o.status = 'PAID'
GROUP BY s.store_id, s.name
ORDER BY paid_order_count DESC, s.store_id;
```

→ 8행. 구매가 없는 두 가게가 사라집니다. **INNER는 양쪽에 짝이 있는 행만, LEFT는 왼쪽 행을 전부 남기고 짝이 없으면 오른쪽을 NULL로 채웁니다.**

### 4-3. 함정 1 : 조건을 ON에 두느냐 WHERE에 두느냐

Q07에서 `o.status = 'PAID'`를 `ON`이 아니라 `WHERE`로 옮기면?

```sql
SELECT s.name, COUNT(o.order_id) AS paid_order_count
FROM store s
LEFT JOIN orders o ON o.store_id = s.store_id
WHERE o.status = 'PAID'
GROUP BY s.store_id, s.name
ORDER BY paid_order_count DESC, s.store_id;
```

→ LEFT JOIN인데도 8행입니다. 짝이 없는 가게는 `o.status`가 NULL이고, `WHERE NULL = 'PAID'`는 참이 아니라서 걸러집니다. LEFT JOIN으로 남긴 행을 WHERE가 다시 지운 것입니다. **오른쪽 테이블 조건은 ON에 두어야 LEFT JOIN의 의미가 유지됩니다.**

### 4-4. 함정 2 : COUNT(*) vs COUNT(컬럼)

Q07의 `COUNT(o.order_id)`를 `COUNT(*)`로 바꿔 보세요.

→ 대전둔산점과 제주공항점이 **1**로 나옵니다. `COUNT(*)`는 행 수를 세는데, LEFT JOIN이 NULL로 채운 행도 한 행이기 때문입니다. `COUNT(컬럼)`은 NULL을 세지 않습니다.

### 4-5. 함정 3 : JOIN하면 행이 늘어날 수 있다

결제 완료 매출 합계를 두 가지로 구해 봅니다.

```sql
SELECT SUM(total_amount) FROM orders WHERE status = 'PAID';

SELECT SUM(o.total_amount)
FROM orders o
JOIN payment p ON p.order_id = o.order_id
WHERE o.status = 'PAID';
```

→ 118,700원과 141,900원. 7번·15번 구매는 결제가 2건이라 JOIN하면 구매 행이 2번씩 나오고, `total_amount`도 2번 더해집니다. (12,400 + 10,800 = 23,200원 차이) **1:N 관계에서 1쪽 값을 N쪽과 JOIN한 뒤 합치면 부풀려집니다.** Q08을 실행해서 7번 구매가 두 줄인 것을 직접 확인해 보세요.

## 5단계. GROUP BY와 집계

### 5-1. GROUP BY 없이 섞으면?

```sql
SELECT store_id, COUNT(*) FROM orders;
```

→ `1140 ... incompatible with sql_mode=only_full_group_by`. `COUNT(*)`는 전체를 한 줄로 합치는데, `store_id`는 20개 중 어느 값을 보여줘야 할지 정할 수 없습니다. `GROUP BY store_id`를 붙이면 "가게별로 한 줄씩"이 되어 해결됩니다.

### 5-2. WHERE vs HAVING

Q09에 매출 2만 원 이상 조건을 붙여 봅니다.

```sql
SELECT s.name, SUM(o.total_amount) AS total_sales
FROM orders o
JOIN store s ON s.store_id = o.store_id
WHERE o.status = 'PAID'
GROUP BY s.store_id, s.name
HAVING SUM(o.total_amount) >= 20000
ORDER BY total_sales DESC;
```

→ 홍대점 24,900원, 강남점 23,500원. **WHERE는 묶기 전에 행을 거르고, HAVING은 묶은 뒤 그룹을 거릅니다.** `SUM(...) >= 20000`을 WHERE에 쓰면 어떤 에러가 나는지도 해보세요.

### 5-3. 왜 unit_price를 따로 저장했나

```sql
SELECT p.name,
       SUM(oi.quantity * oi.unit_price) AS 구매당시_가격으로,
       SUM(oi.quantity * p.price)       AS 현재_가격으로
FROM order_item oi
JOIN orders o  ON o.order_id = oi.order_id
JOIN product p ON p.product_id = oi.product_id
WHERE o.status = 'PAID' AND p.product_id = 12
GROUP BY p.product_id, p.name;
```

→ 우산: 17,500원 vs 18,000원. 우산 가격이 8,500원에서 9,000원으로 올랐기 때문에, 현재 가격으로 계산하면 과거 매출이 바뀝니다. 그래서 `order_item`에 구매 시점 가격을 복사해 둡니다.

**해볼 것:** Q10, Q11을 실행하고 `SUM`을 `AVG`, `MAX`, `MIN`으로 바꿔 보세요.

## 7단계. UPDATE · DELETE · 트랜잭션

### 7-1. 트랜잭션으로 안전하게 실험하기

`START TRANSACTION` 이후의 변경은 `COMMIT` 전까지 확정되지 않고, `ROLLBACK`하면 되돌아갑니다. 한 문장씩 실행하세요.

```sql
START TRANSACTION;
DELETE FROM payment;              -- WHERE 없는 DELETE : 전부 지워짐
SELECT COUNT(*) FROM payment;     -- 0
ROLLBACK;
SELECT COUNT(*) FROM payment;     -- 22, 되돌아옴
```

`WHERE` 없는 UPDATE·DELETE가 얼마나 위험한지 안전하게 확인하는 방법입니다. DataGrip이 실행 전에 경고를 띄울 수 있는데, 위 순서대로라면 진행해도 됩니다.

### 7-2. Q13, Q14 따라가기

Q13을 실행하고 `updated_at`이 바뀌는지 보세요. 직접 값을 넣지 않았는데 바뀌는 이유는 스키마의 `ON UPDATE CURRENT_TIMESTAMP` 때문입니다.

Q14는 `payment → order_item → orders` 순서로 지웁니다. 순서를 거꾸로(`orders` 먼저) 하면 2단계 (g)와 같은 1451 에러가 납니다.

### 7-3. 구매 한 건을 처음부터 끝까지 처리하기

이 DB의 핵심 동작입니다. 강남점(1)에서 삼각김밥(5) 2개를 현금으로 삽니다. 현재 재고는 3개입니다. **한 문장씩** 실행하세요.

```sql
START TRANSACTION;

-- 1. 구매 기록
INSERT INTO orders (store_id, total_amount, status) VALUES (1, 2600, 'PAID');
SET @order_id = LAST_INSERT_ID();   -- 방금 생긴 order_id (MySQL 전용)
SELECT @order_id;                   -- 21

-- 2. 구매 항목
INSERT INTO order_item (order_id, product_id, quantity, unit_price)
VALUES (@order_id, 5, 2, 1300);

-- 3. 재고 차감 : 재고가 충분할 때만
UPDATE inventory
SET quantity = quantity - 2
WHERE store_id = 1 AND product_id = 5 AND quantity >= 2;
SELECT ROW_COUNT();                 -- 1 : 한 행이 바뀜 = 차감 성공

-- 4. 결제
INSERT INTO payment (order_id, method, amount) VALUES (@order_id, 'CASH', 2600);

COMMIT;

SELECT quantity FROM inventory WHERE store_id = 1 AND product_id = 5;  -- 3 → 1
```

이번에는 남은 1개보다 많은 5개를 사려고 합니다.

```sql
START TRANSACTION;
INSERT INTO orders (store_id, total_amount, status) VALUES (1, 6500, 'PAID');
SET @order_id = LAST_INSERT_ID();
INSERT INTO order_item (order_id, product_id, quantity, unit_price) VALUES (@order_id, 5, 5, 1300);

UPDATE inventory
SET quantity = quantity - 5
WHERE store_id = 1 AND product_id = 5 AND quantity >= 5;
SELECT ROW_COUNT();                 -- 0 : 조건에 맞는 행이 없음 = 재고 부족

ROLLBACK;                           -- 앞의 orders, order_item도 함께 취소
SELECT COUNT(*) FROM orders;        -- 21 : 실패한 구매는 남지 않음
```

`AND quantity >= 5` 조건을 빼면 어떻게 될까요?

```sql
UPDATE inventory SET quantity = quantity - 5 WHERE store_id = 1 AND product_id = 5;
```

→ `3819 Check constraint 'ck_inventory_quantity' is violated`. 1 - 5 = -4가 되려는 순간 CHECK 제약이 막습니다. **조건부 UPDATE가 1차 방어, CHECK 제약이 2차 방어**입니다.

> 이 실습은 구매 한 건을 실제로 추가합니다. 끝나면 0장의 방법으로 초기화하세요.

## 8단계. 인덱스

초기화한 상태에서 시작합니다.

### 8-1. 이미 있는 인덱스

```sql
SHOW INDEX FROM orders;
```

→ `PRIMARY`(order_id)와 `fk_orders_store`(store_id) 두 개. 두 번째는 만든 적이 없는데 있습니다. **MySQL은 FK 컬럼에 인덱스를 자동으로 만듭니다.** FK 검사(1452, 1451 에러)를 빠르게 하려면 필요하기 때문입니다.

### 8-2. 인덱스 전후 실행 계획 비교

```sql
EXPLAIN
SELECT order_id FROM orders
WHERE store_id = 1 AND ordered_at >= '2026-11-01' AND ordered_at < '2026-11-08';
```

→ `key = fk_orders_store`, `rows = 6`. 강남점 구매를 전부 찾은 뒤 날짜는 하나씩 확인합니다.

```sql
CREATE INDEX idx_orders_store_ordered_at ON orders (store_id, ordered_at);
```

같은 `EXPLAIN`을 다시 실행하면 → `key = idx_orders_store_ordered_at`, `type = range`, `rows = 3`. 가게와 날짜 범위를 인덱스에서 한 번에 찾아 읽을 행이 줄었습니다.

`EXPLAIN` 읽는 법 (핵심만):

| 컬럼 | 보는 법 |
|---|---|
| `key` | 실제로 쓴 인덱스. NULL이면 인덱스 안 씀 |
| `type` | `ALL`은 전체 훑기(나쁨), `ref`·`range`는 인덱스로 찾음(좋음) |
| `rows` | 읽을 것으로 예상하는 행 수 |

### 8-3. 복합 인덱스는 왼쪽부터

```sql
EXPLAIN SELECT order_id, total_amount FROM orders
WHERE ordered_at >= '2026-11-01' AND ordered_at < '2026-11-08';

EXPLAIN SELECT order_id, total_amount FROM orders
WHERE store_id = 1;
```

→ 첫 번째는 `type = ALL`, `key = NULL`. 두 번째는 `key = idx_orders_store_ordered_at`.
`(store_id, ordered_at)` 인덱스는 전화번호부처럼 가게 순으로 먼저 정렬되고 그 안에서 날짜 순입니다. 날짜만으로는 찾을 수 없고, 가게만으로는 찾을 수 있습니다.

### 8-4. 방금 만든 인덱스를 지워 보기

```sql
SHOW INDEX FROM orders;
DROP INDEX idx_orders_store_ordered_at ON orders;
```

→ `SHOW INDEX`를 보면 `fk_orders_store`가 사라졌습니다. 새 인덱스의 맨 앞이 `store_id`라 FK용으로도 쓸 수 있어서 MySQL이 기존 것을 정리한 것입니다. 그래서 `DROP INDEX`는 `1553 Cannot drop index ... needed in a foreign key constraint`로 거부됩니다. 지우면 FK를 받쳐 줄 인덱스가 없어지기 때문입니다.

**왜 이 컬럼에 인덱스를 걸었나** (과제의 "적용 이유 1줄"): 매장 매출 조회는 거의 항상 "어느 가게의, 언제부터 언제까지"로 묻기 때문입니다. 실제 서비스에서 구매가 수백만 건이 되면 차이가 커집니다. 지금은 20행이라 체감되지 않는 것이 정상입니다.

## 혼자 풀어보기

정답을 펼치기 전에 먼저 작성해 보세요. 초기화한 상태 기준입니다.

**1.** 가격이 1,500원 이하인 상품은 몇 개인가?

<details><summary>정답</summary>

```sql
SELECT COUNT(*) AS cheap_count FROM product WHERE price <= 1500;
```
→ 4개 (생수 500ml, 컵라면, 삼각김밥, 초코바)
</details>

**2.** 홍대점에서 결제 완료된 구매에 대해, 상품별 판매 수량을 많은 순으로 보여라.

<details><summary>정답</summary>

```sql
SELECT p.name, SUM(oi.quantity) AS sold
FROM orders o
JOIN store s       ON s.store_id = o.store_id
JOIN order_item oi ON oi.order_id = o.order_id
JOIN product p     ON p.product_id = oi.product_id
WHERE s.name = '홍대점' AND o.status = 'PAID'
GROUP BY p.product_id, p.name
ORDER BY sold DESC, p.name;
```
→ 초코바 3개가 1위, 이어서 바나나우유·봉지라면·컵라면 각 2개, 7행
</details>

**3.** 가게별로 재고 상품 종류 수와 총 재고 수량을 총 수량이 많은 순으로 보여라.

<details><summary>정답</summary>

```sql
SELECT s.name, COUNT(*) AS product_kinds, SUM(i.quantity) AS total_quantity
FROM store s
JOIN inventory i ON i.store_id = s.store_id
GROUP BY s.store_id, s.name
ORDER BY total_quantity DESC;
```
→ 강남점이 11종 164개로 1위, 신촌점이 5종 50개로 마지막
</details>

**4.** 카드 결제만 대상으로 카드사별 결제 건수를 구하라.

<details><summary>정답</summary>

```sql
SELECT card_company, COUNT(*) AS cnt
FROM payment
WHERE method = 'CARD'
GROUP BY card_company
ORDER BY cnt DESC, card_company;
```
→ 국민·삼성·신한·현대 각 3건, 롯데 2건
</details>

**5.** 결제 완료 구매 중 결제 완료 구매의 평균 금액보다 큰 구매를 찾아라. (서브쿼리)

<details><summary>정답</summary>

```sql
SELECT order_id, total_amount
FROM orders
WHERE status = 'PAID'
  AND total_amount > (SELECT AVG(total_amount) FROM orders WHERE status = 'PAID')
ORDER BY total_amount DESC;
```
→ 평균 약 6,982원, 10건 (가장 큰 것은 7번 구매 12,400원)

서브쿼리 안에도 `status = 'PAID'`가 있어야 같은 기준의 평균이 됩니다.
</details>

**6.** 결제를 두 번 이상 나눠 낸 구매를 찾아라.

<details><summary>정답</summary>

```sql
SELECT order_id, COUNT(*) AS payment_count
FROM payment
GROUP BY order_id
HAVING COUNT(*) >= 2;
```
→ 7번, 15번 구매. `GROUP_CONCAT(method)`(MySQL 전용)를 SELECT에 추가하면 `CARD,CASH`처럼 수단도 한 줄로 볼 수 있습니다.
</details>

**7. (도전)** 가게별로 가장 많이 팔린 상품을 구하라. 결제 완료 기준이고, 공동 1위는 모두 보여라.

<details><summary>정답</summary>

```sql
SELECT store_name, product_name, sold
FROM (
    SELECT s.name AS store_name,
           p.name AS product_name,
           SUM(oi.quantity) AS sold,
           RANK() OVER (PARTITION BY s.store_id ORDER BY SUM(oi.quantity) DESC) AS rnk
    FROM orders o
    JOIN store s       ON s.store_id = o.store_id
    JOIN order_item oi ON oi.order_id = o.order_id
    JOIN product p     ON p.product_id = oi.product_id
    WHERE o.status = 'PAID'
    GROUP BY s.store_id, s.name, p.product_id, p.name
) t
WHERE rnk = 1
ORDER BY store_name, product_name;
```
→ 11행. 강남점은 생수 500ml(5개), 잠실점·판교점·대구동성로점은 공동 1위가 2개씩

`PARTITION BY`는 "가게마다 따로 순위를 매겨라"라는 뜻입니다. 순위로 거르려면 한 번 감싸서(FROM 안의 서브쿼리) 바깥 WHERE에서 걸러야 합니다. 3단계의 실행 순서를 떠올려 보세요.
</details>
